# Relay database

> For maintainers. Using RAS Code? See [docs/user](../user/).

The relay's Postgres is self-hosted and never listens on a public port. Cloudflare Tunnel publishes
it as a hostname, a Cloudflare Access application guards that hostname, and both the Worker and the
deploy host authenticate with the same Access service token.

## Topology

```text
Worker  ──▶ Hyperdrive ──┐
                         ├─▶ Access (code-relay-db.ras.sh) ─▶ Tunnel ─▶ cloudflared ─▶ Postgres
Deploy  ──▶ cloudflared ─┘
            access tcp
```

Everything on the host is a Dokploy service in the `ras-code` project, so it is visible and
manageable from the Dokploy dashboard rather than existing only as loose containers:

| Dokploy service | Kind        | Purpose                                                   |
| --------------- | ----------- | --------------------------------------------------------- |
| `postgres`      | Database    | `postgres:18`, no external port, reachable on the overlay |
| `cloudflared`   | Application | `cloudflare/cloudflared`, runs the named tunnel connector |

The connector reaches Postgres by Docker Swarm service name on Dokploy's overlay network, so the
tunnel ingress targets `tcp://<postgres appName>:5432`. Nothing binds to the host.

## Access paths

The Worker never opens a raw connection. It binds a Hyperdrive configuration whose origin is the
Access-fronted hostname plus the service token, so Cloudflare terminates the Access check before the
Postgres protocol starts.

Migrations run from the deploy host instead, where Hyperdrive is not available. The deploy workflow
opens a loopback tunnel for the length of the deploy and closes it in an `always()` step:

```sh
cloudflared access tcp \
  --hostname "$RELAY_DATABASE_HOST" \
  --url "127.0.0.1:$RELAY_MIGRATION_PORT" \
  --service-token-id "$RELAY_DATABASE_ACCESS_CLIENT_ID" \
  --service-token-secret "$RELAY_DATABASE_ACCESS_CLIENT_SECRET"
```

`RELAY_MIGRATION_DATABASE_URL` then points at `127.0.0.1:$RELAY_MIGRATION_PORT`. The same command
works from a developer machine for a personal stage.

## Databases per stage

Production owns `RELAY_DATABASE_NAME`. Every other stage gets `<RELAY_DATABASE_NAME>-<stage>` on the
same server, so stages never share tables. The deploy role needs `CREATEDB` to provision a new
stage's database.

## Migrations

`applyRelayMigrations` in `infra/relay/src/migrations.ts` applies every generated migration the
database has not recorded, in filename order, each in its own transaction. Applied names live in
`relay_migrations`, so re-running an unchanged directory is a no-op and a failed deploy resumes
rather than restarts. Migration SQL itself is generated by the `Drizzle.Schema` resource from
`infra/relay/src/persistence/schema.ts` and is checked in.

## Deployment credentials

Alchemy resolves one Cloudflare credential, but the two things a deploy needs
disagree about which kind works:

|                         | State store | Minting the relay's scoped API token                    |
| ----------------------- | ----------- | ------------------------------------------------------- |
| OAuth (`alchemy login`) | works       | fails — Cloudflare will not let OAuth grant permissions |
| Scoped API token        | fails       | works                                                   |

The bridge is the state store's own bearer token, cached at
`~/.alchemy/credentials/<profile>/cloudflare-state-store.json`. Once that file
exists, an API token deploys everything. Only OAuth can create it, so CI cannot
produce it and is given a copy instead.

To (re)generate it, on a machine logged in with `alchemy login`:

```sh
alchemy cloudflare bootstrap
```

Then store the file's contents as the `ALCHEMY_STATE_STORE_CREDENTIALS` secret.
The `.github/actions/alchemy-credentials` composite action writes it back, along
with a profile pinned to `method: env` — without that profile a stored OAuth
profile silently outranks `CLOUDFLARE_API_TOKEN`.

`CLOUDFLARE_API_TOKEN` itself needs Workers, Queues, Hyperdrive, KV, R2,
observability and tunnel permissions at the account, `Zone Read` plus DNS and
Workers Routes on the zone, and `Account API Tokens Write` so it can mint the
relay's runtime token.

## Rotating the Access service token

1. Create a replacement token in **Zero Trust > Access > Service Auth**.
2. Add it to the Access application's policy alongside the current one.
3. Update `RELAY_DATABASE_ACCESS_CLIENT_ID` and `RELAY_DATABASE_ACCESS_CLIENT_SECRET` in the
   `production` GitHub environment, then redeploy the relay so Hyperdrive picks up the new origin.
4. Remove the old token from the policy and delete it.
